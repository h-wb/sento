# Codebase review — 2026-10-06

Reviewed revision: `9265e5f` (clean working tree at the start).

The core model is a good fit: a series has publication editions, an edition has stable books, and collected versions express which copies the user wants. Profiles express release preferences; file contents express what is actually on disk. Keep those boundaries, including independent volume and chapter ownership. The highest-value next step is making acquisition, scanning, import, and recovery obey them consistently.

This is an investigation, not an implementation change. The findings below include eleven failures reproduced with temporary focused tests. Application code and the development library were not changed. Additional design recommendations are separated from those reproduced defects.

## Scope and validation

Traced catalog add/refresh/link/merge, local editions, book and version policies, profile scoring, source discovery, search and classification, reservations, multi-client torrent dispatch, queue recovery, archive processing, scans, file organization, calendar/overview projections, and the corresponding frontend flows. Also inspected scheduler behavior, migrations, CI, and the extension sidecar's API and installation code.

## Reproduced correctness findings

### 1. P1 — Upgrade comparisons use zero instead of the current copy's score

Location: [versions.go](../../internal/service/versions.go), lines 268–279 and 365; [funnel.go](../../internal/service/funnel.go), lines 299–313.

`loadLedger` computes the best installed-file score in `best` but never assigns it to `BookStatus.CurrentScore`. `prepareVersions` then copies the zero value into `ownedScores`, and the funnel compares new releases against zero.

Reproduction: an installed LuCaZ copy scores 50, the upgrade cutoff is 100, and the required improvement is 10. Another LuCaZ release also scores 50. The search reports `stored score=0 candidate score=50 rejections=[]` and accepts it as an upgrade. Lower-quality releases can also pass if their score exceeds zero by enough; legitimate improvements from negative scores can be rejected.

Fix direction: carry the recomputed best score into the ledger status, distinguish an unknown score from a real zero, and test equal, worse, insufficiently improved, and sufficiently improved releases through the complete ledger → search path. Existing tests cover upgrade eligibility and pins but miss the comparison itself.

Probe: `TestReviewProbeUpgradeScore`.

### 2. P1 — Chapter discovery cannot start when there are no wanted books

Location: [search.go](../../internal/service/search.go), lines 451–454; [observations.go](../../internal/service/observations.go).

`FindCandidatesStream` returns before querying sources when `wantedBooks` is empty. Discovery happens only after sources return candidates. An empty custom chapter edition therefore cannot discover its first books. A fully collected edition can also stop discovering subsequent chapters until another mechanism creates wanted books.

Reproduction: create an empty local chapter edition, enable discovery, attach a verified active source binding, and enable trust. Searching it never calls the source's chapter listing; it returns “No books can be acquired.”

Fix direction: give discovery its own eligibility check and run it independently of the current wanted-book set. After accepting trusted observations, rebuild the relevant ledger before acquisition. A source-check action should remain available for an empty edition.

Probe: `TestReviewProbeDiscoveryEmptyEdition`.

### 3. P1 — Scanning confirms different books solely because they share a number

Location: [scan.go](../../internal/service/scan.go), lines 202–209.

Search distinguishes main books, extras, and ambiguous duplicate numbers. The scanner instead links every numbered book inside a parsed range. It does not check `CountType`, revision, or uniqueness before marking those links verified.

Reproduction: add an extra with number 1 alongside regular volume 1. Scanning a regular `ONE PIECE v01 (Digital).cbz` produces confirmed links to both books. The same loop can conflate distinct revisions sharing a number.

Impact: the library can claim to own a bonus or revision that the archive does not contain, suppressing acquisition. Manual review is bypassed precisely where stable book IDs were introduced to prevent guessing.

Fix direction: share a pure book-resolution function between search, scan, and import. Resolve number + kind + explicit evidence to unique book IDs; ambiguous matches should enter review. Import's corresponding number-range loop also deserves the same rule, particularly when a user searches a specific extra but receives a regular-volume archive.

Probe: `TestReviewProbeScanDistinctBooks`.

### 4. P1 — Failed routing lookup falls back to the default download client

Location: [torrent.go](../../internal/provider/torrent.go), lines 95–103.

`clientFor` discards an error from loading indexer entries. `wanted` remains empty and the release goes to the default client. A removed/unmatched indexer ID follows the same fallback path.

Reproduction: configure a default direct client and a VPN client, then make the indexer lookup return an error. `clientFor` succeeds and selects the direct client.

Impact: an indexer's explicit network/client restriction can be bypassed during a transient failure. This is more serious than an ordinary failed download.

Fix direction: fail on lookup errors and on a missing previously selected indexer. Use the default only when a successfully resolved indexer explicitly has no client assignment. Resolve and record the client before dispatch.

Probe: `TestReviewProbeRoutingLookupFailure`.

### 5. P2 — A download loses its client identity after dispatch

Location: [torrent.go](../../internal/provider/torrent.go), lines 308–362; [queue.go](../../internal/store/queue.go), `QueueItem`.

Grab chooses a configured client but returns only the torrent hash. Polling and fetch then search all clients and choose the first matching hash.

Reproduction: both direct and VPN clients hold the same hash in different paths. Grab correctly goes to VPN; fetch returns the direct client's `/open` path. Changing client order can change which transfer is observed. Category changes can make an existing transfer disappear from lookup entirely.

Fix direction: persist an explicit download handle containing client ID and remote torrent ID, together with the dispatch destination/category. Poll and fetch that client. Client removal should produce a recoverable “client unavailable” state rather than adoption of another client's torrent. Scope path mappings by client where different hosts use identical remote paths.

Probe: `TestReviewProbeClientOwnership`.

### 6. P2 — Blocklisting misses torrents whose hash was learned during grab

Location: [importer.go](../../internal/service/importer.go), line 484 and the automatic failure path; [provider.go](../../internal/provider/provider.go), `ExternalKey`; [funnel.go](../../internal/service/funnel.go), line 91.

For a feed containing only a GUID/download URL, the candidate's identity is the GUID. Grab later derives the hash from torrent bytes or a redirect. Blocking stores `item.ExternalID` (the derived hash), but the next search checks the original GUID. The same failed release remains eligible.

Reproduction: block a queued download using its derived hash, then evaluate its GUID-only feed entry. It receives no blocklist rejection.

Fix direction: retain the provider/indexer offer identity and its resolved payload/hash aliases. Block against the offer identity and known aliases. The same distinction should drive uncertain-dispatch reconciliation: a feed GUID cannot be looked up as a qBittorrent hash.

Probe: `TestReviewProbeBlocklistDerivedHash`.

### 7. P2 — The queue worker can permanently starve older jobs

Location: [queue.go](../../internal/store/queue.go), lines 122–131; [importer.go](../../internal/service/importer.go), `ProcessQueue`.

The worker uses the same `ORDER BY created_at DESC LIMIT 200` query as the UI. The limit includes `needs_review` and `dispatch_unknown`, which the worker skips without changing their state.

Reproduction: create one runnable job, then 200 newer review jobs. Every worker query returns the 200 review jobs and omits the runnable one. Polling again does not make progress.

Fix direction: separate paginated UI queries from processing queries. Select runnable/due jobs fairly with deterministic ordering and a bounded batch or cursor. Fetch individual queue items by ID for actions instead of searching the most recent 200 history entries.

Probe: `TestReviewProbeQueueLimit`.

### 8. P2 — Replacing an archive at the same path leaves stale verified ownership

Location: [scan.go](../../internal/service/scan.go), lines 113–115; [presence.go](../../internal/store/presence.go).

A known path is always skipped. Presence checks only establish that a file exists; they do not establish that it is still the file whose contents were confirmed.

Reproduction: scan an archive, replace its pages at the same path, and scan again. The row retains the original fingerprint and mappings while reporting the file present.

Impact: replacing or corrupting a library file can leave the UI reporting ownership and prevent a replacement download. Existing manual confirmations may now refer to different bytes.

Fix direction: track enough filesystem metadata to detect likely changes, with an explicit full verification option. When content changes, invalidate old contents/selections as appropriate and require re-evaluation. Do not silently carry manual confirmation across a changed fingerprint. Also make `AddFile` explicitly handle changed content at a known path; its current upsert adds links without removing old ones.

Probe: `TestReviewProbeScanChangedBytes`.

### 9. P2 — Unavailable chapter storage blocks healthy volume storage

Location: [versions.go](../../internal/service/versions.go), lines 152–158 and 240–246; [presence.go](../../internal/store/presence.go).

Presence checks distinguish the two roots, but `loadLedger` reduces all file presence to one series-wide `storageUnavailable` boolean. One unknown/unavailable chapter file then blocks every volume book as well.

Reproduction: the volume directory is readable and the separate chapter directory is absent. A missing volume becomes `storage_unavailable` and is no longer wanted.

Fix direction: evaluate storage availability by the applicable root/edition and relevant assets. Persist root health separately from individual file presence so an unrelated review file cannot disable acquisition for the whole series.

Probe: `TestReviewProbeChapterStorageIsolation`.

### 10. P2 — Supported ZIP/RAR payloads are skipped by torrent import

Location: [importer.go](../../internal/service/importer.go), lines 343–345; [scan.go](../../internal/service/scan.go), `scanExts`.

The archive processor supports ZIP/CBZ and RAR/CBR, but the torrent importer only admits `.cbz` and `.cbr`. A regular ZIP comic never reaches the processor or review-file retention. Scanning supports ZIP but omits RAR.

Reproduction: a valid `ONE PIECE v01 (Digital).zip` imports zero of one expected books and enters partial-import review without retaining the archive in the review area.

Fix direction: define one archive-capability table shared by scan, import, organization, and the UI. Distinguish formats that can be recognized, preserved, and post-processed; do not silently skip a supported comic container.

Probe: `TestReviewProbeZipImport`.

### 11. P2 — Organize files moves additional-only copies into the default version's folder

Location: [organize.go](../../internal/service/organize.go), lines 94–113.

The comment promises to use an additional version when it alone claims the file, but every generated `BookRef` uses `defaultVersion[col.ID]`.

Reproduction: map a file exclusively to “Scanlation copy” and preview organization. The destination is the default `Standard Edition [en]` folder, without the additional version's name. Initial import and later organization therefore disagree about where the copy belongs.

Fix direction: preserve an explicit storage/home version or derive it consistently from eligible selections. For files shared by several versions, choose one documented stable location rather than relying on row order or always forcing default.

Probe: `TestReviewProbeOrganizeAdditionalVersion`.

## Model and architecture recommendations

These are design recommendations and additional inspection findings, not extra passing/failing probe results.

### Preserve the current publication/collection distinction

Keep `Series → Edition → Book` and `Edition → CollectedVersion → Profile`. Local editions and MangaBaka-linked editions should remain the same entity type with different provenance. Retain optional numbers, explicit book IDs, independent volumes/chapters, and conservative cross-edition file mapping. The naming cleanup is helpful; another large rename or ORM/UI-library replacement would not address the current defects.

Make the edition editor answer “Which publication is this?” and the version editor answer “Which releases should Sento keep for it?” The default version can remain implicit until the user needs another copy.

### Separate discovery from acquisition

Discovery answers which books exist; acquisition answers which existing books need a file. They need distinct entry conditions and results, even if they share a background task. Report discovered, awaiting confirmation, and newly wanted counts separately.

Also revisit `scheduler.tickChapters`: it excludes completed series entirely. A completed manga can still have missing chapters or newly available translations. Publication status can change polling frequency; it should not permanently exclude wanted chapter backfill.

Keep the reviewed/trusted observation workflow, but retain accepted source identifiers on books. Currently acceptance creates a numbered main book while the observation remains separate; later matching still relies on numbers. That limits support for source renumbering, special chapters, and multiple distinct entries with the same number. This can be addressed with external references, without reviving a volume↔chapter ontology.

### Represent offers and transfers explicitly

A feed entry, the torrent it resolves to, and a transfer in a particular client are different identities. Persist something equivalent to:

```text
Offer: provider + indexer/source + opaque offer key
Resolved payload: hash or source chapter identity
Transfer: selected client + remote ID + dispatch state
Acquisition plan: version/book claims + evaluation snapshot
```

This can start as additional queue fields and a small alias table. It does not require a new service architecture. Resolve the transfer identity before dispatch where possible, save it durably, then submit. Explicitly distinguish “could not submit” from “submission outcome unknown.” This addresses client routing, blocklisting, retries, and reconciliation together.

### Use one resolver and one fulfillment evaluation across the pipeline

Edition facets are centralized; book resolution is still duplicated in the funnel, scanner, and importer. Introduce a pure resolver returning unique book IDs, unresolved evidence, and ambiguity reasons. Context can supply stronger evidence for a scoped manual choice or verified source binding, but it should not silently bypass contradictory actual-file evidence.

Similarly, expose a structured fulfillment result containing current score, known/unknown facts, eligibility reasons, selected files, and pins. That prevents another score field or rejection reason being computed and then lost between the ledger and search.

Preserve the original release name and original payload filename alongside the current path. `recordAsset` currently sets observed `facts.Title` to the installed filename after renaming, while group/language/quality come from parsing the original filename. Title-based custom formats are then evaluated against Sento's generated name. Renaming should not erase the evidence used to evaluate release quality; make the scoring input and its provenance explicit.

### Finish separating contents from version selections

`asset_contents` is the right distinction. However, `MapFile` deletes and reconstructs intrinsic contents from the submitted version mappings. Removing a book's last version selection can therefore also erase the knowledge that the file contains that book.

Give these operations separate meanings: confirm/correct an archive's contents; select/exclude it for a version; pin a chosen copy. A version change should not rewrite content evidence. Manual correction of content should remain an explicit operation. The UI can present this in two small sections of the existing dialog rather than adding a new page.

### Keep a file identity separate from its content fingerprint

`Fingerprint` hashes sorted page hashes, deliberately ignoring page order. This is useful as a “same images” signal, but it cannot distinguish a release with repaired reading order from the original. It also says nothing about non-image content that `Process` retains. Installation/collision checks currently treat that fingerprint as sufficient equivalence.

Keep the stable file/asset ID; add or retain an exact byte hash for physical verification and an ordered page-content digest for reader-visible equivalence, with the unordered digest optional for duplicate suggestions. Retagging can preserve semantic identity while updating the byte hash. Separate release provenance from shared page content so two genuinely different collected releases do not overwrite each other's facts merely because their images match.

### Treat box contents as explicit publication facts

`SplitBox` always creates volumes `1..count`, copies the box ISBN onto every generated volume, and performs separate transactions for the individual additions and final box changes. That cannot accurately describe box 2 containing volumes 24–46, and the ISBN exported to every book's ComicInfo would be the container's ISBN.

Extend the existing split flow with a first number/range or explicit book selection and a preview. Keep the box's identifier as package provenance; only assign an individual-book ISBN when known. Apply the split and monitoring changes atomically. A narrow package-membership model is sufficient if needed; this does not require automatic equivalence between volumes and chapters.

### Make recovery and metadata changes explicit

The importer checks remote download state before checking whether reviewed local files already fulfill the job. Once the user has resolved every expected book locally, completion should not depend on the torrent still being present in the client. Check verified local fulfillment early and make cleanup best effort.

Manual identity edits are blocked during pending jobs, but catalog refresh can still change edition facts and book numbering. Import reads those current facts while naming uses frozen `BookRef.Number`. Define whether a queued plan remains valid after a catalog correction, and route changed identity to an explicit reconciliation step. Add a catalog/model revision or compare the relevant snapshot fields before import.

Several mutation paths compute important preconditions before acquiring the common transaction lock (version edits, merge/link previews and ownership checks). Move checks and derivation inside the locked transaction where they protect invariants. Concurrency tests should cover these cases; a passing Go race detector does not detect database interleavings.

The extension sidecar also uninstalls an existing extension before the replacement has been downloaded and validated. Stage and validate the replacement first, serialize installations, then swap and atomically persist the manifest. A failed update should leave the previous source usable.

## UX changes tied to the model

- **Show all relevant installed files in a book dialog.** `EditionBooks.bookSelection` passes only satisfactory `fileIds`, and `BookDialog` uses them for its Files tab. A book labeled “Different copy on disk” can open with no file visible. Pass intrinsic on-disk files as well and explain why each does or does not satisfy this version.
- **Disambiguate duplicate book labels.** The mapping selector renders only `sequenceStr`. Include main/extra/other, revision, and a distinguishing title or ISBN when numbers/labels repeat. The user needs enough information to resolve the ambiguity that automation correctly refuses.
- **Separate “Check source for new chapters” from “Search wanted books.”** Make the former useful for an empty or complete edition, and explain discovery/trust controls in those terms.
- **Show the selected client on search confirmation, Activity, and recovery.** Client name plus remote handle makes multi-client behavior understandable and repairable.
- **Make upgrade decisions comparable.** Show current score, candidate score, required improvement, and the main differing facts. A score without that comparison does not explain why Sento wants another copy.
- **Keep file-location previews faithful.** Include the chosen version and resolved collision path, and report skipped/unavailable files independently. Keep actual storage locations until moves succeed; an unsuccessful organize run should not redefine where untouched files live.
- **Preserve errors in background-task status.** Refresh and search sweeps log per-series failures and return success; `GrabBest` likewise logs failures and returns only successful IDs. Aggregate partial failures so System does not report a healthy run while every series failed.

## Suggested implementation order

1. Fix upgrade scores, book-resolution ambiguity, routing fallback, and discovery gating, with the focused reproductions converted into permanent regression tests.
2. Introduce explicit offer/transfer identity; fix client lookup, blocklist aliases, and dispatch reconciliation together. Separate worker queue selection from UI pagination.
3. Add changed-file verification and per-root storage health; unify archive capabilities and make organization preserve a file's version placement.
4. Refine file-content versus selection editing, box contents, and local recovery. Then improve the UI explanations using those same backend results.

Avoid a broad rewrite while doing this. The useful simplification is fewer independent implementations of the same domain rule.
